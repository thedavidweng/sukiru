# Contributing to Sukiru

Thanks for your interest in Sukiru. This guide covers how to report issues,
set up a development environment, and get a change merged.

By participating you agree to follow the [Code of Conduct](CODE_OF_CONDUCT.md).

## Reporting issues

- Search [existing issues](https://github.com/thedavidweng/sukiru/issues)
  first.
- For bugs, include your macOS version, Sukiru version, the output of
  `sukiru-cli capabilities`, and steps to reproduce. A scan report
  (`sukiru-cli scan`) helps, but check it for private paths before posting.
- Report security issues privately as described in [SECURITY.md](SECURITY.md).

## Before you start

Read the [architecture decision records](docs/adr/README.md) and the
[glossary](CONTEXT.md). Two rules shape every change:

- **Zero ledger** ([ADR-0001](docs/adr/0001-pivot-to-zero-ledger-referee.md)):
  Sukiru never writes installer ledgers. Ledger changes go through
  `npx skills` or `gh skill` only.
- **Native red line** ([ADR-0006](docs/adr/0006-pure-swift-apple-native-feel.md)):
  Swift and Apple frameworks only, no third-party UI dependencies, no custom
  chrome, no hard-coded colors or materials.

For larger changes, open an issue to discuss the approach before writing code.

## Development setup

Requirements:

- macOS 14 or later
- Xcode 26 or later (Swift 6.2)
- [XcodeGen](https://github.com/yonaskolb/XcodeGen),
  [SwiftLint](https://github.com/realm/SwiftLint): `brew install xcodegen swiftlint`

```bash
swift test                 # core library and CLI tests
Scripts/build-app.sh       # generate Sukiru.xcodeproj from project.yml and build
Scripts/run-app.sh         # run the debug app
```

`Sukiru.xcodeproj` is generated from `project.yml` and is not committed.

`Scripts/run-app.sh` runs the app binary directly so environment overrides are
inherited. Do not launch a freshly built debug app with `open -F`.

### Environment variables

- `SUKIRU_HOME` replaces `$HOME` for all path resolution. Use it for sandboxed
  launches and tests. A set but missing path is fatal (`sukiru-cli` exits 2).
- `SUKIRU_ROOTS` adds colon-separated project roots.
- `SUKIRU_E2E=1` enables the end-to-end suite against the real CLIs. Cases
  that use `gh` over the network also need `GH_TOKEN`.

**Never run add, remove, or update against your real `$HOME`.** Point
`SUKIRU_HOME` at a fixture or a throwaway sandbox.

```bash
SUKIRU_HOME="$PWD/Fixtures/own-vercel/.home" \
  SUKIRU_ROOTS="$PWD/Fixtures/own-vercel/proj" swift run sukiru-cli scan
SUKIRU_E2E=1 swift test
```

### Fixtures

`Fixtures/` holds the test corpus. Each fixture has an `EXPECTATION.md`
describing what a scan must report. The collision-matrix fixtures (`CM-*`) are
generated by `Scripts/fixtures/generate.sh`, which needs the network, a pinned
`skills` version, and `gh`. Files such as `.DS_Store` inside fixtures are
intentional test data.

### Localization

The app ships in English and Simplified Chinese. Every user-facing string must
be translated in both. After changing UI text, build the app and run:

```bash
Scripts/sync-strings.sh
```

It syncs `App/Resources/Localizable.xcstrings` with the strings the compiler
extracted, the way Xcode does, and fails on stale or untranslated strings. To
preview a language, pass `-AppleLanguages '(zh-Hans)'` to `Scripts/run-app.sh`.

## Quality gates

CI runs these checks on every pull request. Run them locally first:

```bash
swiftlint lint --strict
swift format lint --strict --recursive Sources Tests App
swift test -Xswiftc -warnings-as-errors
Scripts/build-app.sh
```

Format Swift code with the repository's `.swift-format` configuration
(`swift format --in-place --recursive Sources Tests App`).

## Pull requests

- Keep each pull request focused on one change. Do not mix refactoring with
  behavior changes.
- Add or update tests for behavior changes. Core logic belongs in
  `Sources/SukiruCore` and is tested there; the app layer only presents it.
- UI changes: follow the review checklist in ADR-0006 and include screenshots
  in both light and dark mode.
- Record significant design decisions as a new ADR in `docs/adr/` and add it
  to the index.
- Update documentation when behavior changes.

### Commit messages

Use [Conventional Commits](https://www.conventionalcommits.org/). Releases and
the changelog are generated from them by release-please.

```text
feat(health): explain diverging copies
fix: keep empty container directories on rollback
docs: clarify SUKIRU_HOME
```

Common types: `feat`, `fix`, `perf`, `refactor`, `test`, `docs`, `build`,
`ci`, `chore`.
